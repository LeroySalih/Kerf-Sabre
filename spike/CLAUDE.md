# spike/ (throwaway)
Single-file `spike.py` (pyserial required, opencv optional) plus a Linux-runnable build script producing the portable Windows zip. Laser at S0 except the optional test 11. Ctrl-C or exception: send `!` then `0x18`, close port, still write the report. Tests use a mocked serial port. Operator results go in `spike/results/<station>/`.

## Logging (so any problem can be diagnosed from the folder alone)
Each run writes `output/<station>_<time>/` and a `.zip` of it: `session.log` (one readable timeline: TX/RX with times, what the screen showed, what the operator typed, events, warnings for timeouts/partial lines/GRBL errors, errors with tracebacks), `serial.log` (JSON lines of TX/RX with raw bytes when they differ from the text), `results.jsonl` and a partial `report.json` saved after every test (so a hang or crash still leaves results), `report.json`/`report.txt`, `env.txt` (written at the start, includes pyserial version, hostname, argv, timezone, USB devices), `settings.txt` (`$$`), and `crash.log` (faulthandler: native crashes, and a stack dump if one test is stuck for 3 minutes). Port-open failures say what to check (another program holding the port, driver). `tests/test_spike.py` checks all of this.

## Spike 2: GCC Mercury III (station 5) - `mercury_probe.py`
The Mercury III (probably a Ruida controller, run from Techsoft 2D Design over USB, no camera) is not GRBL, so the Falcon tests do not apply. `mercury_probe.py` is a **read-only identification run**: it sends nothing to the laser (a test asserts this). It records USB devices (with their driver service), COM ports, printers and printer drivers, laser-related software, processes, services, network adapters, software folder file names and small settings files, and guides the operator through unplugging and replugging the USB cable so the laser's own USB device is identified by the difference. `interpret()` turns that into hints: a serial driver means a COM port exists; WinUSB means Python can reach it over USB (pyusb); a vendor driver means Python cannot without that driver's DLL or a driver swap; a GCC printer entry means 2D Design may print to a Windows driver (a different route from G-code). Run with `run_mercury_probe.bat` from the same portable zip; results go in `spike/results/<station>/` like spike 1. The next spike (active tests: connect, read status, jog, stop) is written once these results say which route to use.
