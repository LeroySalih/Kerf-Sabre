# cutter/ (BISAK Kerf Cutter: the Creality Falcon Cutter)
Spike gate met (all four station PCs pass; see `docs/spike-results.md`). The plan is `cutter/PLAN.md`; read it and `docs/spike-results.md` before non-trivial work. Build in milestone order (M0 first).

Rules: portable-folder deployment, JSON-lines logging with raw serial TX/RX, rotating local logs, diagnostic bundle, outbound-only connection, feed hold + reset on any fault. Read `$30`, never assume. Never `G92`. Device (COM port and camera) selection is stored as match rules and managed explicitly, never hard-coded. Own folder only; `shared/` changes need a version bump and a `shared/CHANGELOG.md` entry, one feature at a time.

Tests: `pytest` from `cutter/` against the simulated GRBL in `tests/fake_grbl.py`.

## Status (read this first)
Built and tested against the simulated GRBL and the real Server: M0 (config, JSON-lines logs with rotation, ship queue, remote level, token redaction), M1 (GRBL link: reset-to-banner, interruptible commands, `Hold:0` wait, alarm decoding), M2 (device manager: saved match rule {vid, pid, location, lastPort}, AMT/SOL never probed, busy detection, `--devices`), M3 (G-code scan: G21/G90, no G92/G91/G20/`$`, S <= `$30`, every move on the bed incl. arcs; job runner with stop/pause/resume and the fault policy), M4 (WebSocket client against the real `/ws/cutter`: hello, status, progress, ack, result, controls, frame, G-code download + SHA-256, reconnect), M5 (camera capture thread, JPEG in memory only; real cameras untested), M6 (diagnostic bundle, remote log level), M8 (`build_cutter.py` portable Windows zip). **Not done:** M5 camera names/enumeration (index only; the plan's DirectShow-name probe still has to run on a station PC), the M7 contract bump (devices screen, `home`/`reset_alarm` commands), and M9 (on-station trial: nothing has run on a real laser yet).
- Layout: `kerf_cutter/` (`config`, `logs`, `station` = the state machine and wiring, `grbl/{state,link,gcode,jobrun}`, `devices/{ports,manager}`, `camera/capture`, `net/{client,http}`, `diag/bundle`), `build_cutter.py`, `package/` (the .bat files and README that ship in the zip), `tests/` (`fake_grbl.py` is the simulator; `test_station.py` runs the Cutter against the real Server over a real WebSocket and needs `pip install -e ../server`).
- Rules that bite: a job or frame runs as a background task so the receive loop can still hear Stop (an integration test caught this); while streaming or framing the Cutter reports a busy state to the Server even when GRBL's buffer is momentarily empty; after any stop, fault or alarm the machine is reset so it homes again (`auto_home`) before the next job; the job's size is compared with the server's `bounds` using the feed moves only (the file ends with a rapid back to the origin); a lost server connection during a cut holds and resets after `ws_loss_grace_s` (5 s, proposal pending the owner's answer to plan question 2); homing (`$H`) runs after start, stop and alarm (plan question 3, same).
- **GRBL answers some lines only when the motion has finished.** `M5`, `M9`, `M3`/`M4`, `G4`, and any move when the planner is full do not return `ok` until the queued moves have run, which on a slow cut is minutes. The first real cut failed with "The laser stopped answering at line 36 of 38 (M9)" after 15 s while the status still said `Run`. `Link.command(..., busy_limit=)` now asks `?` when the timeout passes and keeps waiting while the laser reports Run/Hold/Jog/Home, up to `JobRunner._busy_limit()` (`max(60, estimated*3+30)` s, the same allowance as the final wait for idle); an Idle, Alarm or silent laser is still a timeout at once. `tests/fake_grbl.py` has `slow_ok` to simulate it.
- The Cutter's plain HTTP calls (`net/http.py`: G-code download, diagnostic upload) send `User-Agent: kerf-cutter/<version>`. Behind Cloudflare the default `Python-urllib/3.x` agent is answered **403** before the request reaches the Server (the Cutter's WebSocket still connects, so the station shows "Connected · Idle" but every job fails with "The server answered 403 for .../gcode"); `tests/test_http_agent.py` fakes that. A refusal now also quotes the first 200 characters the other end said (Cloudflare's "error code: 1010").
- The portable Python reads `python311._pth`, whose paths are relative to the `python\` folder: it must list `..` (the folder holding `kerf_cutter`) or `-m kerf_cutter` fails with "No module named kerf_cutter" (this shipped broken once; `tests/test_build.py` now checks it).
- Build: `python3 cutter/build_cutter.py [--no-camera]` makes `cutter/build/kerf-cutter.zip` (needs the internet once); the Server offers it on the Admin site's Cutter software page when it exists (`KERF_CUTTER_ZIP` or that path), otherwise the pretend Cutter. `start.py` and `server/run-local.sh` build it best-effort.

Console echo (`logs.py` `CutterLog(echo=sys.stdout)`, on by default; `--quiet` turns it off): every event and **every serial command and reply** is printed as it happens (`12:34:56.789 TX G1 X10 Y10 S500`, `... RX ok`, `... INFO frame_start job_id=... bounds=...`), even with the log level at INFO (raw serial lines then stay out of the file and the shipped log, as before). The token is redacted as in the file. The practice Cutter (`server/kerf_server/devtools/fake_cutter.py`) prints everything the Server sends it and the G-code it pretends to run (`TX`/`RX`).
